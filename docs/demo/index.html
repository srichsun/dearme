背後發生的事

    一般後端動作 花錢的模型呼叫 寫進儲存

    工程品質

    這個專案我最在意的七件事，以及每一件實際做了什麼。

    可測試

    93 個測試，但不打真的模型。

    • 塞一個假模型進去，資料庫用記憶體 SQLite——不花錢、兩秒跑完，也不會因為模型今天回答不一樣就無故變紅。
    • 假模型還能測真模型測不到的：我可以叫它故意漏寫一段，看程式撐不撐得住。

    可觀測

    AI 會很有自信地講錯話，所以要能查。

    • 每個回答都列出它讀了哪幾天——日期是從工具的輸出抓的，不是模型講的，所以造不了假。
    • LangSmith 留下每次呼叫的 prompt、工具參數、token、延遲。有人說答錯了，我打得開現場。

    成本可控

    每個花錢的地方都有天花板，全部在一支檔案裡。

    • budget.py 打開就知道錢花在哪：分析一天 3 次、摘要一天 3 次、讀 60 天、答案上限 2048 token。
    • 寫日記不計次，分析才計次——存文字不花錢，對寫字收費等於在懲罰認真寫的人。

    資料正確

    規則寫在資料庫和型別裡，不是靠程式記得。

    • 一天一篇是唯一索引擋的——寫第二篇不是被拒絕，是做不到。
    • 向量的 id 就用 SQL 主鍵，所以刪得準。我踩過一次只刪 SQL 忘了刪向量，AI 就記得一個已經不存在的版本。

    可擴展

    寫一年之後，一次呼叫餵進去的量跟第一週差不多。

    • 摘要是滾動更新的：只讀最近 60 天，更舊的靠上一版帶下來；撈回的事實也有上限（24 條）。資料一直長，prompt 不會。
    • 下一個瓶頸我知道在哪：pgvector 目前沒有建向量索引。幾百條事實用暴力搜尋沒問題，到幾十萬條就需要 HNSW。還沒到那個量，現在加是為一個還不存在的問題付代價。

    好維護

    註解寫「為什麼」，不只寫「做什麼」。

    • 做什麼看程式碼就知道，會消失的是當初的理由——為什麼要加這個鎖、為什麼這個錯誤刻意讓它過。
    • 換模型只改一支檔案。OpenAI 把我的模型下架那天，我改一行就修好了。

    安全

    把權限拿掉，不是靠檢查擋掉。

    • 每個查詢都把 uid 寫進 where——猜 id 的結果是查無此筆，不會有「先載入別人的資料再擋掉」這個中間狀態。
    • Agent 的工具沒有 user_id 這個參數，模型看不到也填不了。安全不能建立在「模型會乖乖聽話」上面。

    還缺的：告警。我踩過一次外部模型被下架，日誌裡躺著 404，但沒有人通知我——是自己去用才發現。這讓我學到健康檢查要真的碰到相依服務，不然它只是在告訴你伺服器還活著。

    開發時最難的三件事

    照難度排，不是照時間。前兩個是設計上的判斷，第三個是上線之後才學得到的。

    01

    長期記憶要怎麼設計

    難在哪
    三個需求互相打架：要記得夠久（三個月前的事也撈得回來）、不能越來越貴（不可能每次把整本日記塞進 prompt）、要撈得準（撈回一堆不相關的，答案就歪了）。
    怎麼做
    參考了 Mindsera 的做法——把日記拆成原子事實、歸進固定分類、檢索時讓模型自己挑要搜哪幾類。他們那八個分類我一字不差沿用，另外加了 wins 和 gratitude，因為我的畫面要一天一天顯示這兩個。
    踩到的
    一開始我是一天存一個向量，結果很糟：一天會寫工作、睡眠、家人，三件事混在同一個向量裡，搜「睡眠」時分數被另外兩件事稀釋，撈不回來。改成一條事實一個向量之後就乾淨了。
    結論
    記憶分三層，因為問題本來就有三種：「3/18 發生什麼」用純 SQL、「以前有過類似的嗎」用向量、「我是個怎樣的人」用LLM 濃縮的摘要。該用 SQL 的地方就用 SQL，不是什麼都丟去做向量搜尋。
    還缺的
    Mindsera 有定期清理（每月重生分類、丟掉過時的事實），我沒有。事實只會累積，寫久了會有「兩年前早就不成立的事還在被撈回來」的問題。

    02

    改產品，讓架構和成本問題一起消失

    難在哪
    這個專案原本是聊天形式，事實抽取每一輪都要跑——等於在使用者跟他的回覆之間，插進一次 LLM 呼叫加一輪 embedding。很慢。
    本來的解法
    看起來很明確：上任務佇列。Celery 加 Redis，再養一個不能縮到零的常駐 worker。多三個要維運的東西，而且不管有沒有人用，每個月都在燒錢。
    實際做的
    把產品改成一天一頁的日記。抽取就自然變成使用者主動按的動作，整個延遲問題直接不存在了，那三樣東西也都不用養。
    成本也一起解了
    抽取變成使用者主動按之後，沒人按就是零成本——不是有一台機器在那邊空轉等工作。同一個決定也讓「一天三次」這種上限變得自然：計次落在真的花掉模型呼叫的動作上，寫日記本身完全不計次。
    學到的
    延遲問題最便宜的解法，常常是產品決定，不是基礎設施。我沒有把非同步做好，我是讓那個需求不存在。

    03

    外部依賴會靜默失效

    難在哪
    使用者說問教練沒反應。但 App 是活的、健康檢查綠燈、Cloud Run 一切正常。我完全沒有動過任何程式碼。
    查出來
    日誌裡躺著 404 — 這個模型已經被下架。OpenAI 淘汰了我寫在設定裡的模型。
    三層
    換掉模型名稱 → 又炸：新模型預設會 reasoning，而 reasoning 跟工具呼叫在那個端點上不相容。
    關掉 reasoning → 又炸：第三方套件的執行緒競態（它的單例旗標在建構完才設，我的 agent 平行呼叫工具剛好撞上）。
    每修好一層，才看得到下一層。前兩個把第三個遮住了——那個競態其實一直都在，只是從來沒執行到那裡。
    學到的
    健康檢查要真的碰到相依服務，不然它只是在告訴你伺服器還活著。
    還有：測試塞假模型跑得快又免費，但測不到真 API 的行為改變——所以我現在改動模型層之後，會另外打一次真的 API。

    效能與記憶體

    不算最難，但是實際量過、也實際改過的部分。

    延遲不是等比例成長的

    難在哪
    教練的回答可以唸出來。但語音合成的耗時隨長度超線性成長——實測一句話回來要 0.6 秒，整段回答要 11 秒。使用者按下播放，要等超過十秒才有聲音。
    沒有用的解法
    換更快的供應商沒有意義，因為問題不在單價而在曲線。無論誰做，長文字都會比短文字慢得不成比例。
    實際做的
    前端把回答切成約 220 字元的句子，播第一段的同時去抓第二段。因為唸一段的時間大約是合成一段的十倍，所以第一段之後永遠有下一段等在那裡，接縫聽不出來——第一聲大約 1 秒就出來。同一段文字只合成一次，之後從快取拿，重播不再花錢。
    另一個延遲問題
    模型呼叫的逾時本來全部是 20 秒。摘要改成四段之後輸出變長，20 秒直接把它砍斷，使用者只看到失敗。現在分成兩種：會串流的回答 20 秒（卡住就該快點失敗）、一次吐一大包的 120 秒。
    規格與現況
    Cloud Run 512 MiB / 1 vCPU，並發 80、最多 20 個實例；30 天日誌裡零筆記憶體超限。模型客戶端在匯入時就建好、全程重用，省下每次請求重建的時間——代價是常駐佔記憶體，這個規格綽綽有餘。
